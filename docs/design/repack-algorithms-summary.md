# Repack 两个核心整理算法：节点腾空法 vs 集中度法（讲解版）

> 面向评审/分享的通俗讲解。目标：讲清楚**两个算法各自的思路、擅长的场景、优劣势**，以及**怎么选**。
> 权威技术细节见 `repack-policy-design.md` §4.14 / §4.17；本文是"能听懂"的汇总版。

---

## 0. 先说结论（一页记住）

- 两个算法**目标完全一样**：把散落在很多节点上的 GPU/NPU 占用**拢紧**，**腾出整机空节点**，让排队的大作业能调度下来。
- 区别只在**怎么搜这个整理方案**：
  - **方案 A · 节点腾空法**——**自顶向下**，盯着"节点"，一个个把它腾空。像**清空并合并仓库**。
  - **方案 B · 集中度法**——**自底向上**，盯着"每个作业"，让它往更满的节点凑，靠一个"集中度分数"爬坡。像**往更满的箱子里塞东西**。
- 一句话点破关系：**A 是 B 的"批量特例"**——"腾空一个节点"就是集中度分数的一次大跳变。**不是两个目标，是同一目标的两种找法。**
- **在我们的目标场景（AI 负载、卡数多为 2 的幂、节点同构），两者腾出的节点数基本一样。** 所以选型不是比"谁腾得多"，而是比**"快稳可运维" 还是 "统一可演进"**。

---

## 1. 为什么需要整理（一分钟背景）

作业反复起停，会让空闲卡**碎**在很多节点上：集群总空闲卡够，但没有**连续的整机空位**，需要"整机 8 卡 / 跨机 64 卡"的大作业就一直排队。

整理 = 在**保证被挪的作业都能重新落下**（这条硬约束叫 INV-RESCHED，搬家不是抢占）的前提下，把零散负载拢紧、腾出整机。两个算法都在这个框架里跑，区别只是"搜索方式"。

---

## 2. 方案 A · 节点腾空法（drain）

### 思路（打个比方）
像**清仓合并**：挑一个"最容易清空"的仓库（节点），把它里面的货（作业）搬到别的仓库的空位里；**只有能整个清空，才真的搬**——清不空就不动它，换下一个。

### 一轮怎么跑（4 节点 ×8 卡的例子）
```
整理前：N1=6/8  N2=4/8  N3=2/8  N4=2/8    （散，凑不出整机）
① 腾 N4：把 N4 的 2 卡塞进 N1 的空位 → N1 满(8)，N4 清空 ✔（腾出 1 台）
② 腾 N3：把 N3 的 2 卡塞进 N2 → N2 满(8)，N3 清空 ✔（腾出 2 台）
整理后：N1=8  N2=8  N3=0  N4=0            （腾出 2 台整机）
```
外层循环是"**节点**"（收益单位），内层把要搬的作业用装箱（FFD/best-fit）塞进别处碎片，沙箱验证能落下才**原子提交**。

### 擅长的场景
- **批量、周期性**整理（排进维护窗口那种）。
- **大规模商用、重运维**：动作单元（节点）正好等于运维动作（cordon/drain），SRE 有现成心智模型。
- 想要**快、稳、可预测、马上能上**。

### 优势
- **直达目标**：每提交一次 = 腾出一个整机，报表天然是"将腾空 N3/N4"，可直接签核。
- **扰动天然有界**：只动"被腾节点"上的负载，其它一律不碰。
- **零空转**：原子提交，不会搬来搬去停不下来。
- **几乎零配置**：排序固定，难配错、易评审、易定位。
- **已实现 + 已验证**（`orchestrator.go` + 单测 + Python 交叉校验）。

### 劣势
- 贪心是"定好顺序扫一遍"，**偶尔会卡在局部最优**（个别多节点协同的机会抓不到）。
- **偏批量/离线**，在线增量整理弱（集群一变要全量重算）。
- 加新策略（优先级/拓扑/成本）要塞进"选谁搬 + 节点排序 + 多方案择优"多个点，**扩展偏硬**。

## 3. 方案 B · 集中度法（consolidation）

### 思路（打个比方）
给整个集群打一个**"集中度分数" = 每个节点用量的平方和（Σ 用量²）**；**只做能让分数变大的搬迁**。分数越大 = 负载越扎堆 = 空出来的节点越多。

**为什么用"平方"（点睛）**：平方让"扎堆"比"摊平"值钱——同样 8 张卡，放成 `(8,0)` 得 **64**，放成 `(4,4)` 只得 **32**。所以"把分数做大"自动等于"逼负载往一起凑、把节点腾空"。

### 一轮怎么跑
从当前状态出发，**逐个作业**看："把它挪到某个更满的节点，分数会不会涨？" 涨就走这一步，一直爬到不能再涨（局部最优）。这就是"爬山"。
> 补一句可信度：这套东西在学术上叫**势博弈**，在云厂商那边就是**虚拟机整合（VM consolidation）**的标准做法。

### 擅长的场景
- **持续 / 在线**整理（集群一直在变，随时小步整理）。
- 平台团队想要**一个统一、能讲清、能调权重**的算法贯穿始终。
- **策略变更频繁**：想通过调权重达到不同效果，而不是改代码。

### 优势
- **叙事最统一**：全靠一个"集中度分数"，概念上最好讲。
- **最好演进**：决策是**单一净分** `净收益 = Σ收益项 − λ·Σ扰动项`；加任何新维度（优先级/拓扑/碳/成本，甚至 P1 的 relief 解救排队作业）= **注册一个打分函数 + 配个权重**，不碰主循环。
- **天然在线增量**：集群变了，只重算受影响的少数作业。
- 能逃出 A 的**部分**局部最优（多节点协同），理论上限略高一点点。

### 劣势
- **目标间接**：分数涨了不一定真多腾出节点，**必须**加"只提交净腾空子集"的闸门，否则会**空转（thrashing，搬来搬去）**。
- **要调参**：λ、各项权重、阈值——灵活但**多团队多集群下容易配错**。
- **对一线运维不友好**：单步理由抽象（"这步让分数 +Δ"），故障要回放整条爬山轨迹，move 散在全集群、故障半径弥散。
- **朴素实现慢**：复杂度约 O(N³)，大集群单次跑到分钟级（有成熟的增量优化能追平 A，但要额外做）。
- 设计完成、**待编码**（`consolidate.go` 已有初稿 + 单测）。

## 4. 一张表看懂差异

| 维度 | A · 节点腾空法 | B · 集中度法 |
|---|---|---|
| 思路 | 自顶向下，盯节点，一个个腾空 | 自底向上，盯作业，往更满处凑、爬分 |
| 对目标 | **直达**（每次提交=1 个整机） | 间接（靠分数代理 + 净腾空闸门） |
| 效果上限 | 偶尔卡局部最优 | 略高（可逃部分局部最优） |
| 目标场景实际差距 | — | **通常可忽略**（两者腾的节点数一样） |
| 扰动可控 | **天然有界** | 靠 λ + 闸门调 |
| 空转风险 | **无** | 有，必须加闸门 |
| 可讲性 | 好（"腾哪几个节点"） | **最好**（单一分数叙事） |
| 在线/增量 | 弱（批量重算） | **强** |
| 可运维/可定位 | **最好**（= cordon/drain，零配置） | 抽象分数 + 大配置面，一线负担重 |
| 可演进（加新策略） | 偏硬 | **最好**（加打分函数 + 权重） |
| 复杂度 | ~O(N²)，Go 里 sub-second | 朴素 ~O(N³)，需增量优化 |
| 状态 | **已实现 + 验证** | 设计完成，待编码 |

> 小字：两者被**同一个理论最优卡住**（最多腾 `B−A` 个节点），"腾的节点数"不是靠换算法能突破的。

## 5. 什么时候选哪个

| | 更适合 A | 更适合 B |
|---|---|---|
| 整理节奏 | 批量、周期性、排维护窗口 | 持续 / 在线 |
| 团队取向 | 要快、稳、可预测、已落地 | 要统一、可讲、可调、长期演进 |
| 策略变更频率 | 低 | 高（常调权重） |
| 谁来运维 | 一线 SRE 友好 | 平台团队友好 |
| 评审通过难度 | **低**（已实现、风险小） | 中（需认可势函数 + 调参） |

## 6. 选型建议（三条路线，供拍板）

1. **只上 A（最快最稳）**：P0 直接用已实现的节点腾空法，风险最低、最易评审、快速见效。代价：可演进/在线性弱。
2. **只上 B（最统一最可演进）**：集中度法作主算法，A 退为可选兜底。一个能讲清、能调权重的算法贯穿始终。代价：要编码 + 调参、有已知坑（设计已给解法）。
3. **A 作基线 + B 作精修（最稳健、上限最高）**：先 A 出安全解，再 B 爬山精修、"只采纳净增空节点"。鲁棒性和上限最好，代价是两套都要维护。

**倾向性建议（非定论，交评审）**：
- 若目标是 **P0 快速落地 / 大规模商用重运维** → **路线一（A）**：已就绪、运维友好。
- 若更看重 **统一、可演进、可在线持续整理** → **路线二（B 为主）**。
- **抉择点是"快速稳妥 + 可运维" vs "统一可演进"的团队权重，而不是"谁腾的节点多"**（目标场景下二者收益基本持平）。
- 长期可演进为 **"A 出可见提交 + B 内部精修"** 的混合（路线三），待 B 的可观测/权重治理/回放调试工具成熟后再切。

## 6.5 结合 AI 生产场景：为什么方案 A 更契合

现实的 AI 生产集群有两个特点，直接把选型推向 **A**：

**前提① 作业尽量不被中断。** 两个算法都要驱逐/重建作业（严格说都有中断），但 **A 的扰动天然有界、且零空转**——只动"被腾节点"上的负载、原子提交、绝不搬来搬去；B 靠 λ 摩擦 + 闸门去防 thrashing，本质上仍有"额外无谓搬迁"的风险。按"把中断降到最少"，**A 更稳**。

**前提② 碎片率低（个位数）、集群较满、很少大量空节点。** 碎片少 = 要动的本来就少。这时 **A 的"精准挑几个节点腾、每次提交必有一个整机收益、开销 O(N²) 亚秒级"** 正好用在刀刃上；而 **B 的全局爬山在小碎片下是"杀鸡用牛刀"**，它的强项（在线持续、逃多节点局部最优）在这种规模基本用不上。低碎片 + 高利用率，恰恰奖励 A"整空才提交"的纪律——不产生整机就不动任何东西。

**结论**：就"少中断、低碎片"的 P0/生产诉求，**选方案 A**。B 的价值是长期平台向的（统一可讲、可插拔演进、在线持续整理），可作 P1，或后续"A 出可见提交 + B 内部精修"的混合。

> 一句话：目标场景下两者腾的节点数其实差不多；抉择点是"少中断 + 好运维"——这恰是 A 的主场。

## 7. 讲的时候的三个"金句"

1. **"两个算法一个目标，只是找法不同——A 像清仓合并，B 像往更满的箱子塞。"**
2. **"平方那句：8 张卡放成 (8,0) 得 64、放成 (4,4) 只得 32——所以'把分数做大'就等于'把节点腾空'。"**
3. **"目标场景下谁腾的节点都差不多；真正的抉择是——要 A 的'快稳可运维'，还是 B 的'统一可演进'。"**
